# US-028 — Verificare il rischio 4 (atomicità eterogenea delle scritture)

## Descrizione
Come maintainer del layer di persistenza, voglio sapere per ogni archivio che cosa succede se una scrittura viene interrotta, affinché si decida dove la scrittura diretta richieda una scrittura atomica.

## Business Rules
- Stato di partenza: deduzione. Sono atomici (file temporaneo e rinomina) la configurazione di lint, il database di import schedulato e le revisioni di embedding; non lo sono le sessioni agente e la cronologia (scrittura diretta). Per gli altri archivi dipende dalla scrittura generica di file, non letta: la chiude US-015.
- Su Windows la ricostruzione dell'indice elimina prima l'originale: finestra non atomica (wiki).
- Metodo ammesso: **sola lettura del codice** (Q_003). Nessuna esecuzione dell'applicazione, nessuna interruzione simulata, nessuna modifica al repository del cliente.

## Acceptance Criteria
- [ ] L'esito parte dall'ipotesi come in wiki e si ottiene per sola lettura del codice; per ogni conclusione sono riportati i file e i simboli letti.
- [ ] La tabella di atomicità per archivio (da US-015) è confermata o corretta per lettura: per ogni archivio, scrittura diretta oppure file temporaneo con rinomina.
- [ ] Per gli archivi con scrittura diretta è riportato, per lettura, cosa il codice di caricamento fa se il file è troncato o vuoto (valore di default, errore, sostituzione alla scrittura successiva), con rimando a US-021 e alla pagina dei file corrotti.
- [ ] È riportato, per lettura, il passaggio non atomico della ricostruzione dell'indice su Windows (eliminazione dell'originale prima della rinomina) e cosa legge un lettore concorrente nella finestra.
- [ ] L'esito è dichiarato confermato, smentito o non conclusivo per lettura, archivio per archivio; se confermato, è indicato l'impatto sui dati.
- [ ] Dove la sola lettura non basta (per esempio garanzie del file system o della libreria di scrittura), l'esito è «non conclusivo» e il motivo è dichiarato.
- [ ] Nessuna esecuzione dell'applicazione e nessuna modifica al repository del cliente.
- [ ] Il dossier unico di EP-004 (`raw/<data>-repo-llm_wiki-dossier-ep004.md`, scritto da `repo-sync` senza Bash e per sola lettura del codice; più dossier con slug distinti se troppo grande) riporta per questo rischio i file letti, le evidenze e l'esito proposto; `wiki-keeper` lo ingerisce e registra l'esito in wiki. Nessun esito è scritto direttamente in `wiki/`.
