# llm-wiki — archivi di persistenza
> I dati di `llm-wiki` vivono su file: 17 archivi per progetto in `.llm-wiki/` più lo store `app-state.json` del plugin Tauri; una sola versione di formato è dichiarata in modo esplicito.

## Contesto
Pagina ricavata dalla seconda estrazione di `repo-sync`, mirata al layer di persistenza, sullo stesso commit `e08cfce` (ramo `develop`). Il campione di questo giro è di 21 file, tutti sotto 50.000 byte. Il repository è di terzi, sotto GNU GPL v3: la pagina riporta solo nomi di file, simboli e campi, con parole proprie. [^src: raw/2026-11-20-repo-llm_wiki.md §Premessa e perimetro]

Convenzioni del raw: tutti gli archivi in `<progetto>/.llm-wiki/` sono per progetto; «TS» indica il frontend, «RS» il backend Rust; dove non è dichiarata una versione di formato il raw scrive «nessuna». Il file di dati mancante o illeggibile viene letto quasi ovunque in modo silenzioso, con valore vuoto o di default. [^src: raw/2026-11-20-repo-llm_wiki.md §Inventario degli archivi]

### Sincronizzazione con Rust e segreti
- I commenti di `project-store.ts` indicano che i nomi `proxyConfig` e `apiConfig` devono coincidere con quelli letti dal codice Rust; se divergono, l'API resta senza token configurato. [^src: raw/2026-11-20-repo-llm_wiki.md §Schemi e campi]
- Tra i campi in chiaro (deduzione non testata) compaiono `token` e `localToken` in `mineruConfig`; per `apiConfig` i commenti parlano di un token API. Nessun valore è stato letto. I tipi di `llmConfig`, `embeddingConfig`, `searchApiConfig` e `providerConfigs` sono in `src/stores/wiki-store.ts`, non letto: la presenza di chiavi API non è verificata. ### Nota sulla cronologia
La cronologia è una mappa file-per-percorso con indirizzo stabile (hash FNV-1a a 64 bit con costanti fisse, per resistere ai cambi di toolchain). Il record di `scheduled-import-db.json` tiene un hash md5 per file e, in più, size e mtime per saltare il ricalcolo. [^src: raw/2026-11-20-repo-llm_wiki.md §Schemi e campi]

### `app-state.json`
- Lato TS lo store è aperto con il nome relativo `app-state.json`, con salvataggio automatico attivo e valori di default vuoti (osservato); un commento dichiara che il salvataggio automatico è un debounce di 100 ms. [^src: raw/2026-11-20-repo-llm_wiki-persistenza-a.md §Store applicativo (`app-state.json`)]
- Il TS forza il flush su disco solo per `proxyConfig`, `apiConfig`, `generalConfig`, `scheduledImportConfig:<percorso>`, `sourceWatchConfig`, `sourceWatchAllProjects` e `zoomLevel` (osservato). Per `llmConfig`, `providerConfigs`, `searchApiConfig`, `embeddingConfig`, `multimodalConfig` e `mineruConfig` si affida al solo salvataggio automatico. [^src: raw/2026-11-20-repo-llm_wiki-persistenza-a.md §Store applicativo (`app-state.json`)]
- Lato Rust il plugin store è registrato senza opzioni, la capability della finestra principale include `store:default` e l'identificatore dell'app è `com.llmwiki.app` (osservato). Il Rust non usa il plugin per leggere: legge il file con le API del file system componendo `app_data_dir()` con il nome `app-state.json`, in tre punti (`lib.rs` due volte, `api_server.rs` una). [^src: raw/2026-11-20-repo-llm_wiki-persistenza-a.md §Store applicativo (`app-state.json`)]
- Che il file letto dal Rust sia lo stesso scritto dal plugin lato frontend è affermato dagli autori nei commenti di `proxy.rs`; non è verificato in esecuzione. Restano non verificati il percorso fisico per sistema operativo e il comportamento del plugin su file corrotto (gap `llm-wiki-app-state-percorso`). [^src: raw/2026-11-20-repo-llm_wiki-persistenza-a.md §Store applicativo (`app-state.json`)]
- Lettori Rust (letto): oltre a `proxyConfig` e `apiConfig`, il Rust legge dallo stesso file `projectRegistry` e `recentProjects`, `embeddingConfig`, `llmConfig`, `searchApiConfig` (con `searchApiConfig.anyTxt`) per il runtime dell'agente e, in `api_server.rs`, `sourceWatchConfig` per id progetto o `default`. La copia di `load_agent_runtime_config` in `api_server.rs` passa dalla cache di 5 secondi; la copia in `lib.rs` legge senza cache a ogni avvio di turno agente. [^src: raw/2026-11-20-repo-llm_wiki-persistenza-a.md §Punto 4: lettori di `app-state.json` in `api_server.rs`]

### Meccanismo di scrittura per archivio
- Per i moduli TS la fonte è il `writeFile` generico, quindi scrittura diretta, salvo dove indicato. Diretta: `project.json`, `ingest-queue.json` (scritture serializzate in processo da una coda di richieste, errori ignorati), `ingest-cache.json` (lettura-modifica-scrittura dell'intero file, errori ignorati), `review.json`, `lint.json`, chat (`conversations.json` per primo, poi un file per conversazione), `chat-preferences.json`, `dedup-not-duplicates.json`. Atomica (`writeFileAtomic` o file temporaneo e rinomina): `embedding-revisions/*.revision`, `lint-config.json`, `scheduled-import-db.json`. Gestita da lancedb: le due tabelle vettoriali (la v1 cancella e aggiunge in due passi). Plugin store con salvataggio automatico con debounce e flush esplicito per alcune chiavi: `app-state.json`. Per cronologia `history/<hash>.json` e sessioni agente il raw riporta «diretta» dalla prima estrazione, non riletta. [^src: raw/2026-11-20-repo-llm_wiki-persistenza-b.md §Atomicità per archivio]
- `history-settings.json` ha scrittura non verificata: in `file_history.rs` sono lette solo le righe 1-70 (percorso e tipo); resta la dichiarazione in blocco «cronologia: diretta» della prima estrazione. [^src: raw/2026-11-20-repo-llm_wiki-persistenza-b.md §Atomicità per archivio]
- Comandi Rust: `write_file` e `write_file_base64` sono diretti (`fs::write` sul percorso finale); `write_file` marca prima il percorso come scrittura dell'app (il watcher la ignora) e registra versioni di cronologia «baseline» e dopo la scrittura; `write_file_atomic` scrive un file `.<nome>.<nanosecondi>.tmp` accanto al target e poi rinomina (rimuove il temporaneo se la rinomina fallisce). Tutti richiedono un percorso assoluto lato TS e creano le cartelle padre. [^src: raw/2026-11-20-repo-llm_wiki-persistenza-b.md §Scrittura generica (Rust e TS)]
- Zero occorrenze della stringa `sync_all` in `fs.rs`: non risulta flush su disco. Deduzione dichiarata dal raw: l'atomicità vale per i lettori concorrenti, non è dimostrata come durabile a un crash. Lo zero vale per la stringa letterale. [^src: raw/2026-11-20-repo-llm_wiki-persistenza-b.md §Scrittura generica (Rust e TS)]

### Code, cache e didascalie
- `dedup-queue.json` è un array di `DedupTask` (`id`, `projectId`, `group`, `canonicalSlug`, `status` pending, processing, done o failed, `addedAt`, `error`, `retryCount`); i task `done` non sono salvati; scrittura diretta, errori ignorati; un file illeggibile dà una coda vuota; alla riapertura i `processing` tornano `pending`, i `pending` restano in pausa finché non si riprende a mano e i task di altri progetti si scartano; ritentativi 3. `lint.json` è un array di `LintItem` (`id` forma `lint-N`, `type`, `severity`, `page`, `detail`, `affectedPages?`, `brokenTarget?`, `suggestedTarget?`, `suggestedSource?`, `createdAt`); i valori ammessi di `type` e `severity` sono in `lint.ts` e il tipo `DuplicateGroup` in `dedup.ts`, non letti. [^src: raw/2026-11-20-repo-llm_wiki-persistenza-b.md §Coda di dedup e lint]
- `saveIngestCache` si chiama dopo la scrittura dei file, solo se sono stati scritti file e non ci sono fallimenti duri né blocchi troncati non recuperati; la lettura considera valida una voce solo se tutti i file in `filesWritten` esistono ancora. [^src: raw/2026-11-20-repo-llm_wiki-persistenza-b.md §Cache di ingest, didascalie e checkpoint]
- `image-caption-cache.json` esiste come archivio: mappa chiave-voce con `caption`, `mimeType`, `model`, `capturedAt`, `imageHash?`, `outputLanguage?`; chiave uguale all'hash SHA-256 dei byte (legacy) oppure all'hash seguito da `::language:` e lingua codificata; scritto una volta a fine batch solo se ci sono didascalie nuove; file mancante o corrotto dà mappa vuota con avviso in console.
